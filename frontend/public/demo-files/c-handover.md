# 배포

운영 배포는 화요일과 목요일 오후 2시에만 한다 — 이번 주도 같은 원칙으로, 화·목이 아니면 배포일이 아니다. 금요일과 공휴일 전날에는 배포하지 않는다. 배포는 혼자 하지 않고, 시작 전에 배포 채널에 이번에 배포할 PR 목록과 롤백 담당자를 먼저 적어둔다.

배포 승인은 팀 리드가 한다 — 배포 채널에 PR 목록을 올리면 팀 리드가 확인 이모지를 남기는 것으로 승인을 대신한다. 승인 없이 배포를 시작하지 않는다.

배포 일정(어떤 PR이 이번 배포에 들어가는지)은 배포 채널 상단에 고정된 '이번 주 배포 목록' 글에서 확인한다.

## 운영 배포 절차

배포할 PR은 main에 머지되고 스테이징에서 30분 이상 문제가 없어야 한다. 스테이징 확인은 '스테이징 모니터링' 대시보드(그라파나)로 하고, 에러율·응답 시간 그래프에 이상이 없는지 본다.

배포 순서는 다음과 같다: ① 배포 채널에 이번 배포에 들어갈 PR 목록과 롤백 담당자를 적는다 ② 팀 리드의 승인 이모지를 확인한다 ③ CI의 'deploy-prod' 워크플로를 수동 실행한다(실행은 배포 담당자 본인이 한다) ④ 배포가 끝나면 15분 동안 에러율 대시보드를 지켜본다 ⑤ 이상이 없으면 배포 채널에 "배포 완료 + 배포된 PR 번호"를 남긴다. 배포는 보통 5~10분 안에 끝나고, 그 뒤 15분 관찰까지 합치면 전체 20~25분 정도 걸린다.

배포 기록(누가, 언제, 무엇을 배포했는지)은 CI의 'deploy-prod' 실행 이력에 전부 남고, 배포 채널 게시글로도 같이 남는다. 스테이징 주소는 https://staging.내부도메인 이고 사내망에서만 접속된다.

## 롤백

배포 후 에러율이 평소의 2배를 넘으면 원인을 찾기 전에 먼저 롤백한다 — 1.5배처럼 기준(2배) 미만이면 바로 롤백하지 않고 먼저 원인을 살펴본다.

롤백은 'deploy-prod' 워크플로를 직전 태그로 다시 실행하면 된다. DB 마이그레이션이 포함된 배포는 코드만 되돌리면 안 되므로 반드시 사수에게 먼저 알린다. 롤백 후에는 에러율이 평소 수준으로 돌아왔는지, 롤백으로 인해 새로 발생한 오류는 없는지 15분 더 지켜본 뒤 배포 채널에 롤백 완료를 남긴다.

# 온콜

온콜은 주 단위로 돌아가며, 첫 한 달은 사수와 함께 2인 1조로 선다. 온콜 교대는 매주 월요일 오전에 이루어지고, 교대 시간과 담당자는 온콜 캘린더(사내 캘린더 'oncall')에 미리 등록되어 있다.

## 장애 대응

장애 등급은 SEV1(전체 서비스 중단), SEV2(일부 기능 또는 일부 사용자에게 영향), SEV3(영향은 있으나 우회 가능하거나 소수 사용자만 영향) 세 단계로 나눈다. 등급은 온콜 담당자가 1차로 정하고, 애매하면 사수나 팀 리드와 상의해 최종 확정한다.

알림이 오면 5분 안에 장애 채널에 '확인 중'을 남긴다. 장애 알림은 모니터링 시스템에서 슬랙 '장애' 채널로 자동 전송된다. 사용자 영향이 있으면(에러가 실제 사용자 요청에서 발생하고 있으면) 등급을 SEV2 이상으로 올린다.

장애 상황은 제일 먼저 장애 채널에 남기고, 이어서 팀 리드에게 개인 메시지로도 알린다 — 채널만 보고 놓칠 수 있어서 이중으로 알린다. 복구 후에는 에러율, 응답 시간(p95), 요청 성공률 세 지표가 평소 수준으로 돌아왔는지 확인한 뒤 '복구 완료'로 남긴다.

원인을 모르는 상태에서는 최근 배포부터 의심하고, 30분 안에 해결되지 않으면 사수를 호출한다. 최근 배포가 없는데 장애가 나면 외부 요인(트래픽 급증, 외부 API 장애, 인프라 이슈)부터 대시보드에서 확인한다.

로그는 로그 시스템(내부 Kibana)에서 서비스명으로 검색해서 본다. 대시보드(그라파나) 접근은 입사 시 자동으로 부여되며, 안 보이면 팀 리드에게 계정 연결을 요청한다.

장애가 끝나면 48시간 안에 회고 문서를 쓴다. 회고 문서 양식은 위키의 '장애 회고 템플릿'을 복사해서 쓰고, 원인·타임라인·재발 방지 항목을 채운다. 재발 방지 항목은 회고 문서의 '재발 방지' 섹션에 적고, 담당자와 기한까지 함께 적어야 한다.

장애 공지(사용자·사내 대상)는 장애 채널이 아니라 '서비스 공지' 채널에 별도로 올린다. 온콜 인수인계는 교대 시점에 열려 있는 이슈와 지난주 장애 요약을 온콜 캘린더 메모에 남기고 다음 담당자에게 직접 구두로도 전달한다.

## 알림 기준

API p95 응답 시간이 1초를 넘거나 5xx 비율이 1%를 넘으면 알림이 온다. 알림 기준 값은 모니터링 시스템의 '알림 규칙' 페이지에서 확인할 수 있다. 야간(23시~8시)에는 SEV2 이상만 전화로 호출된다 — 그 외 알림은 슬랙으로만 오고, 아침에 확인해도 된다.

야간 알림은 등록된 온콜 담당자 전화로만 오고, 슬랙 알림도 동시에 남는다. 5xx 비율 알림이 오면 먼저 최근 배포 여부와 특정 API에 몰려있는지(전체 vs 일부 엔드포인트)부터 대시보드에서 확인한다.

알림을 잠시 끄려면(예: 알려진 이슈로 반복 알림이 울릴 때) 모니터링 시스템에서 해당 알림 규칙을 최대 1시간까지 '일시 중지'할 수 있다 — 끄고 나서 원인 해결 없이 방치하지 않는다.

p95가 0.9초처럼 기준(1초) 근처에서 계속 머무르면, 알림이 안 울렸더라도 팀 채널에 미리 공유해 둔다 — 곧 기준을 넘길 수 있다는 신호다. 같은 알림이 반복해서 울리면 근본 원인을 먼저 고치는 게 우선이고, 기준 자체를 조정하려면 팀 리드와 상의해야 한다(담당자 임의로 기준을 바꾸지 않는다). 같은 알림이 짧은 시간에 여러 번 오는 건 모니터링 시스템이 자동으로 하나로 묶어 보여주므로 따로 처리할 필요는 없다. 테스트 중에 뜬 알림도 실제 알림과 구분해 장애 채널이 아닌 개발 채널에라도 남겨서, 나중에 통계에 섞이지 않게 한다.

알림 기준을 서비스별로 다르게 두는 것도 가능하다 — 모니터링 시스템에서 서비스 단위로 규칙을 따로 만들 수 있는데, 이건 팀 리드와 상의해서 결정한다.

# 개발 환경

로컬 개발 환경과 권한은 입사 첫 주에 모두 준비한다. 로컬 DB는 docker compose로 띄운다(자세한 명령은 아래 '로컬 개발 환경' 참고). 환경 구성 과정은 위키 '로컬 개발 환경 세팅' 문서로 이미 정리돼 있고, 새로 겪는 문제가 있으면 그 문서에 추가해 나간다 — 자동화 스크립트도 이 문서를 기반으로 만들어져 있어서, 문서로 자동화해두자는 제안은 이미 반영된 상태다.

## 로컬 개발 환경

로컬 환경 세팅 순서는 다음과 같다: ① 저장소를 클론한다 ② `.env.example`을 `.env`로 복사하고 팀 리드에게 받은 환경 변수 값(사내 문서함의 '로컬 환경변수' 문서에서도 받을 수 있다)을 채운다 ③ `docker compose up -d` 명령으로 DB와 캐시를 띄운다 ④ `make seed`로 시드 데이터를 넣는다 ⑤ 로컬 서버를 실행해 정상 동작을 확인한다.

로컬 API 서버는 8000번, 로컬 DB는 5432번, 캐시(Redis)는 6379번 포트를 쓴다. 운영 데이터는 절대 로컬로 내려받지 않는다 — 일부만이라도 마찬가지로 안 된다. 필요한 데이터는 시드 스크립트로 만들거나 팀 리드에게 익명화된 샘플을 요청한다.

## 권한 신청

저장소 쓰기 권한은 입사 당일, 스테이징 접근은 첫 주에 받는다. 스테이징 접근 권한은 위키의 '권한 신청' 문서에 있는 신청 양식을 작성해 팀 리드에게 제출하면 1영업일 안에 부여된다. 운영 DB 조회 권한은 입사 한 달 뒤에 신청할 수 있다.

권한 신청 절차를 입사 체크리스트에 미리 넣어두면 신입이 매번 위키를 찾아보지 않아도 되므로, 필요하다고 판단되면 팀 리드에게 체크리스트 항목 추가를 제안해도 된다.
