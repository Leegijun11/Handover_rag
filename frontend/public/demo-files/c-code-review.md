# 브랜치 규칙

브랜치는 main에서 따고, 작업 하나에 브랜치 하나를 쓴다.

## 브랜치 이름

'유형/티켓번호-요약' 형식으로 짓는다. 예: feature/PLAT-231-login-rate-limit. 유형은 feature, fix, chore 중 하나다.

## 커밋 메시지

첫 줄은 무엇을 바꿨는지 50자 안에 쓰고, 본문에 왜 바꿨는지를 적는다. 티켓 번호는 본문 끝에 둔다.

# 코드 리뷰

모든 PR은 리뷰어 1명 이상의 승인을 받아야 머지할 수 있다.

## PR 올리기

PR 설명에는 변경 이유, 테스트 방법, 배포 시 주의할 점을 적는다. 400줄이 넘는 PR은 쪼갤 수 있는지 먼저 검토한다.

## 리뷰 응답

리뷰 요청은 하루 안에 응답한다. 바로 보기 어려우면 '내일 오전 확인' 같은 댓글이라도 남긴다.

지적 사항에 동의하지 않으면 이유를 적어 논의한다. 말없이 무시하고 머지하지 않는다.

# 머지

승인과 CI 통과가 모두 끝나야 머지한다.

## 머지 방식

squash merge를 기본으로 한다. 커밋 이력을 남겨야 하는 큰 작업만 리뷰어와 합의해 merge commit을 쓴다.

## 머지 후

머지한 브랜치는 바로 삭제한다. 배포가 필요한 변경이면 다음 배포일 배포 채널 목록에 PR을 올린다.
