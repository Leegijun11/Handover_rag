# 2. 공통 데이터 모델

> 여기 정의된 필드명·타입은 전 모듈이 동일하게 사용합니다.
> 수정 권한은 조장에게만 있으며, 임의로 필드를 추가·변경하지 않습니다.

---

## 2-1. User (사용자)

**용도**: 신입사원과 사수를 구분하는 최소 단위. 1차 빌드에서는 이메일 인증(메일 발송) 없이, 이메일+비밀번호 기반 회원가입/로그인으로 생성됨.

**담당**: 팀원 B

```python
class User(BaseModel):
    user_id: str
    name: str
    email: str
    password_hash: str
    role: Literal["newcomer", "mentor"]   # 신입 / 사수(기존사원)
```

| 필드 | 설명 |
|---|---|
| `user_id` | 생성 시 발급되는 고유 id. 이후 모든 모델이 이 id를 참조 |
| `email` | 로그인 식별자로만 사용. 실제 인증 메일 발송·확인 절차는 없음 (2차 확장 항목) — 가입 시 중복 여부만 검증 |
| `password_hash` | 평문 비밀번호는 저장하지 않고 해시만 저장. **API 응답에는 절대 포함하지 않음** (응답 시 이 필드 제외한 별도 반환 모델 사용) |
| `role` | `"newcomer"`(신입) 또는 `"mentor"`(사수/기존사원) |

## 2-2. Assignment (신입-사수-문서 배정)

**용도**: 어느 신입이 어느 사수의 어느 인수인계서를 배정받았는지 연결. 챗봇이 검색 범위를 결정할 때, 리포트가 누구를 대상으로 계산될지 결정할 때 모두 이 모델을 거침.

**담당**: 팀원 B

```python
class Assignment(BaseModel):
    assignment_id: str
    newcomer_id: str      # User.user_id (role="newcomer")
    mentor_id: str          # User.user_id (role="mentor")
    document_id: str        # 이 신입에게 배정된 인수인계서
    assigned_at: datetime   # 최초 배정 시각 — 재배정(문서 교체)해도 값 유지
```

| 필드 | 설명 |
|---|---|
| `newcomer_id` | 배정 대상 신입 |
| `mentor_id` | 배정한 사수. 한 사수가 여러 Assignment를 가질 수 있음(1:N) |
| `document_id` | 배정된 인수인계서. 챗봇은 이 문서 범위 안에서만 검색 |
| `assigned_at` | 이 신입이 **최초로** 배정받은 시각. 같은 신입에게 문서를 재배정해도(3-1 참고) 이 값은 갱신하지 않음 — `/report/generate`가 최초 리포트의 `period_start` 기본값으로 쓰는 기준(3-6)이 이 필드라, 재배정 때마다 초기화되면 리포트 기간이 매번 리셋되는 문제가 생김 (신규 필드 — 팀원 B가 재배정 시나리오 검토 중 발견) |

> 한 신입은 원칙적으로 하나의 활성 Assignment를 가진다고 가정 (1차 빌드 기준. 신입 한 명이 여러 문서를 동시에 배정받는 경우는 범위 밖)

## 2-3. Document / DocumentChapter (인수인계서)

**용도**: 업로드된 인수인계서를 챕터 단위로 구조화해서 저장. 이 챕터 구조가 챗봇 검색 매칭, 체크리스트 작성, 리포트의 영역별 분류(히트맵) 기준으로 계속 재사용됨.

**담당**: 팀원 A (문서 처리 모듈에서 생성)

```python
class DocumentChapter(BaseModel):
    chapter_id: str           # 문서 내에서 고유 (예: "1-1")
    document_id: str           # 어느 인수인계서에 속하는지
    title: str                  # 예: "입고 처리"
    parent_id: str | None       # 상위 챕터 id (최상위는 None)
    content: str | None          # 원문 텍스트 (순수 그룹핑용 상위 챕터는 None 가능)
```

| 필드 | 설명 |
|---|---|
| `chapter_id` | 같은 문서 안에서만 고유하면 됨 (여러 사수가 각자 문서를 올리므로, 서로 다른 문서에 `"1-1"`이 중복 존재할 수 있음 — 반드시 `document_id`와 함께 사용) |
| `document_id` | 이 챕터가 속한 문서. 챗봇 검색 시 배정된 문서로 필터링하는 기준 |
| `parent_id` | 계층 구조 표현용. 최상위 챕터는 `None` |
| `content` | 원문 텍스트. **순수 그룹핑용 상위 챕터**(예: "1. 입고 관리"처럼 제목만 있고 실제 내용은 하위 챕터 "1-1", "1-2"에 다 있는 경우)는 `None` 가능 — 이런 챕터는 청킹/임베딩(`DocumentChunk`) 대상에서 제외하고, 체크리스트 초안 생성(`/checklist/draft`)에서도 건너뜀 (내용이 없으니 LLM에 넘길 게 없음). 실제 본문이 있는 챕터는 항상 `content`를 채움 (신규 — content가 없는 중간 챕터 케이스를 원래 스펙이 놓치고 있었음, `parent_id`처럼 null 허용으로 수정) |

```python
class DocumentChunk(BaseModel):
    chunk_id: str
    document_id: str            # ChromaDB 검색 시 배정 문서로 필터링하는 데 사용
    chapter_id: str              # DocumentChapter.chapter_id 참조
    text: str
    embedding: list[float]
```

## 2-4. ChatLog (챗봇 질문 로그)

**용도**: 신입사원의 모든 질문과 처리 결과를 기록. 리포트 생성의 원재료.

**담당**: 조장 (챗봇 모듈에서 생성)

```python
class ChatLog(BaseModel):
    log_id: str
    newcomer_id: str
    document_id: str
    question: str
    answer: str
    answered: bool
    matched_chapter_id: str | None
    question_type: Literal["fact", "procedure", "judgment", "advanced"]
    created_at: datetime
```

| 필드 | 설명 |
|---|---|
| `document_id` | 이 질문을 한 시점에 신입에게 배정돼 있던 문서. 신설 — 재배정(3-1) 후에도 "이 대화는 어느 문서에 대한 것인지" 구분할 수 있게 함. `matched_chapter_id`는 답변 실패 시 `None`이라 문서 구분 용도로 못 쓰지만, 이 필드는 질문마다 항상 채워짐 |

| 필드 | 설명 |
|---|---|
| `answer` | 실제 답변 본문(고정 문구 포함). 신설 — 원래 스펙엔 없었는데, 답변 텍스트를 어디에도 저장하지 않아서 신입이 챗봇 화면을 벗어났다 돌아오면(재배정 등 다른 화면 이동만 해도) 대화가 전부 사라지는 문제가 있었음. 프론트가 `GET /chat/logs`로 이전 대화를 복원할 수 있도록 추가 (팀원 B 지적으로 발견) |
| `newcomer_id` | 질문한 신입사원. (기존 `user_id`에서 명칭 변경 — 챗봇은 신입만 사용하므로 명확히 함) |
| `matched_chapter_id` | 검색으로 매칭된 챕터. 이 값이 속한 문서는 항상 해당 신입의 Assignment.document_id와 같음 |
| `question_type` | 성장 곡선 신호(①)에 사용되는 질문 성격 분류 |

> 답변은 항상 `Assignment.document_id`로 스코프가 제한된 검색 결과를 근거로 생성됨. `answered = false`인 로그는 신입 화면에는 "담당자에게 문의하세요"로만 노출되고, 별도로 HR 리포트용 집계 대상이 됨 (실시간 문서 보강 제안 없음)

## 2-5. ChecklistItem (체크리스트)

**용도**: 온보딩 태스크 목록. 사수가 직접 작성하거나 AI 초안을 승인해서 등록하며, 완료 여부와 시점이 리포트의 태스크-질문 매칭, 침묵 구간 판단에 사용됨.

**담당**: 조장(초안 생성 API) + 팀원 A(편집·승인·저장)

```python
class ChecklistItem(BaseModel):
    item_id: str
    newcomer_id: str            # 이 항목이 속한 신입
    chapter_id: str | None      # 사수가 선택적으로 연결. 없으면 None
    title: str
    order: int
    status: Literal["pending", "done"]
    completed_at: datetime | None
    source: Literal["manual", "ai_draft"]
```

| 필드 | 설명 |
|---|---|
| `newcomer_id` | 이 체크리스트 항목의 대상 신입 (신규 추가 — 누구의 체크리스트인지 명시하는 필드가 기존엔 없었음) |
| `chapter_id` | 문서 챕터와의 선택적 연결. 여러 사수가 여러 문서를 올리므로, 연결 시 반드시 해당 신입에게 배정된 문서(`document_id`)의 챕터여야 함 |
| `source` | `"manual"`(사수 직접 작성) / `"ai_draft"`(AI 초안에서 승인) |

## 2-6. AdaptationReport (적응도 리포트)

**용도**: ChatLog + ChecklistItem을 집계해서 만드는 최종 산출물. HR 화면에만 노출.

**담당**: 조장 (리포트 생성 모듈에서 생성)

```python
class ReportSection(BaseModel):
    signal_type: Literal["growth_curve", "chapter_heatmap", "gap_task", "silence_risk"]
    summary: str
    data: dict

class AdaptationReport(BaseModel):
    report_id: str
    newcomer_id: str
    period_start: datetime
    period_end: datetime
    generated_at: datetime
    sections: list[ReportSection]
```

| 필드 | 설명 |
|---|---|
| `newcomer_id` | 누구의 적응도 리포트인지 (기존 `user_id`에서 명칭 변경) |
| `period_start` / `period_end` | 이 리포트가 다루는 데이터 기간 |
| `generated_at` | 실제로 이 리포트가 생성된 시각. 히스토리 목록 정렬 기준 |
| `sections` | 4가지 신호(성장곡선/영역별 히트맵/완료-이해 불일치/침묵 위험) |

## 2-7. 모델 간 참조 관계 요약

| 모델.필드 | 참조 대상 | 어디서 쓰이나 |
|---|---|---|
| Assignment.newcomer_id / mentor_id | User.user_id | 신입-사수 연결, 챗봇 검색 범위 결정 |
| Assignment.document_id | DocumentChapter.document_id | 챗봇 검색 범위 제한 |
| ChatLog.newcomer_id | User.user_id | 질문 주체 식별 |
| ChatLog.matched_chapter_id | DocumentChapter.chapter_id | 영역별 히트맵(신호②) |
| ChecklistItem.newcomer_id | User.user_id | 체크리스트 소유자 식별 |
| ChecklistItem.chapter_id | DocumentChapter.chapter_id | 태스크-질문 매칭(신호③) |
| ChatLog.created_at + ChecklistItem.completed_at | — | 침묵 구간 판단(신호④) |
| ChatLog.question_type | — | 성장 곡선(신호①), 문서 구조와 무관 |
