## 5-3. 서버 통합 방식

각 모듈은 `router.py`에 `router = APIRouter()`를 정의하고, `main.py`가 이를 모아 등록하는 구조로 통일합니다.

```python
# main.py (조장이 프로젝트 초기에 뼈대를 만들어두고, 이후 각자 자기 라우터 import 줄만 추가)
from fastapi import FastAPI
from routers.user import router as user_router
from routers.assignment import router as assignment_router
from routers.document import router as document_router
from routers.checklist import router as checklist_router
from routers.checklist_draft import router as checklist_draft_router
from routers.chat import router as chat_router
from routers.report import router as report_router

app = FastAPI()

app.include_router(user_router)
app.include_router(assignment_router)
app.include_router(document_router)
app.include_router(checklist_router)
app.include_router(checklist_draft_router)
app.include_router(chat_router)
app.include_router(report_router)
```

- **실행 명령어**: `uvicorn main:app --reload` (전원 동일 명령어로 실행)
- **포트**: `8000` 고정
- `main.py`는 조장이 Day 1에 먼저 뼈대를 만들어 커밋해두고, 이후 각자 자기 라우터의 import·include 두 줄만 추가하는 식으로 씁니다 (이 두 줄 추가는 임의 변경 금지 규칙 예외 — 자기 라우터 등록은 자유롭게 추가 가능)
- `.env` 로딩: `main.py` 최상단에서 `from dotenv import load_dotenv; load_dotenv()`를 라우터 import보다 먼저 호출합니다. 이게 없으면 `.env`를 아무리 채워도 무시되고 `core/` 모듈들의 `os.getenv(...)` 기본값(예: JWT 시크릿 등)으로 조용히 폴백되어 전원이 똑같이 영향을 받으니 주의 (팀원 B 지적으로 발견, A-3)

### 5-3-1. DB 모델(`models/`) 공용 Base

- `core/database.py`에 `Base = declarative_base()`를 두고, `models/`의 각 파일은 이 `Base`를 상속해서 테이블 클래스를 정의합니다 (파일명은 `schemas/`와 1:1, 담당자도 동일 — 5-2 참고)
- `main.py`가 모든 `models/*.py`를 import한 뒤(각자 라우터 import 줄 추가할 때 같이 추가) `Base.metadata.create_all(bind=engine)`을 한 번 호출해서 테이블을 생성합니다. 1차 빌드 범위에서는 Alembic 같은 마이그레이션 도구 없이 이 방식으로 충분 (팀원 B 제안 채택, A-1)
- `models/`(SQLAlchemy, DB 테이블용)와 `schemas/`(Pydantic, API 요청/응답용)는 필드가 겹쳐 보여도 역할이 다르므로 둘 다 유지 — `schemas/`를 지우고 `models/`만 쓰지 않습니다

## 5-4. 환경변수 (.env) 규칙

| 변수명 | 용도 |
|---|---|
| `OPENAI_API_KEY` | OpenAI API 키 |
| `MYSQL_HOST` | MySQL 호스트 |
| `MYSQL_PORT` | MySQL 포트 |
| `MYSQL_USER` | MySQL 사용자 |
| `MYSQL_PASSWORD` | MySQL 비밀번호 |
| `MYSQL_DATABASE` | 사용할 DB 이름 |
| `CHROMA_PERSIST_DIR` | ChromaDB 로컬 저장 경로 (예: `./chroma_data`) |
| `JWT_SECRET_KEY` | JWT 서명 키 |
| `JWT_EXPIRE_MINUTES` | 액세스 토큰 만료 시간(분). 예: `1440`(24시간) |

- 실제 값이 담긴 `.env`는 커밋하지 않고, `.env.example`에 변수명만 채워서 공유
- ChromaDB는 문서 단위(`document_id`)로 컬렉션을 분리해서 저장 (`collection_name = document_id`) — 이렇게 하면 여러 문서가 섞여도 서로 침범하지 않음

## 5-5. 에러 응답 규칙 (HTTP 상태코드 매핑)

| 상황 | 상태코드 |
|---|---|
| 정상 조회/처리 | 200 |
| 생성 성공 (POST로 리소스 생성) | 201 |
| 요청 스키마 검증 실패 (필수 필드 누락, 타입 불일치 등) | **422** (FastAPI/Pydantic 기본 동작 그대로 — 애초에 400으로 못박았던 게 프레임워크 관례와 안 맞았음, 팀원 B 지적으로 수정, A-2) |
| 그 외 요청 형식 오류 (잘못된 JSON 등) | 400 |
| 인증 토큰 없음/만료/위조 | 401 |
| 토큰의 신원·역할과 요청 대상이 불일치 (권한 없음) | 403 |
| 존재하지 않는 리소스 조회 (없는 user_id, document_id 등) | 404 |
| 배정(Assignment) 없이 챗봇 등 호출 | 404 |
| Rate limit 초과 | 429 |
| 서버 내부 오류 (LLM 호출 실패 등) | 500 |

모든 비정상 응답 바디는 3번 문서(3-7)에서 정한 공통 포맷을 그대로 씁니다: `{"error": true, "message": "..."}`. FastAPI/slowapi 기본 동작은 상황별로 바디 모양이 제각각(`{"detail": "..."}`, `{"detail": [...]}`, `{"error": "..."}`)이라 그대로 두면 이 규칙이 안 지켜짐 — `main.py`에 아래 세 가지를 전역 예외 핸들러로 등록해서 항상 공통 포맷으로 통일합니다 (조장 담당, A-2):
- `HTTPException` → `{"error": true, "message": exc.detail}`
- `RequestValidationError`(422) → `{"error": true, "message": "..."}` (Pydantic이 만든 상세 에러 리스트는 message 안에 요약해서 넣거나 생략, 재량)
- `RateLimitExceeded`(429) → `{"error": true, "message": "..."}` (slowapi 기본 핸들러 대신 이 포맷으로 직접 작성)
- 위 세 개가 못 잡는 나머지 `Exception` 전부(DB 연결 실패 등 예상 못한 에러) → 500 + `{"error": true, "message": "서버 내부 오류가 발생했습니다"}` — 이 catch-all이 없으면 FastAPI 기본 500 텍스트 응답("Internal Server Error")으로 새서 공통 포맷이 깨짐 (실제로 재현해서 발견, A-2 후속)

모든 비정상 응답 바디는 3번 문서(3-7)에서 정한 공통 포맷을 그대로 사용합니다: `{"error": true, "message": "..."}`

## 5-8. 배포 (필수 — 대회 규정상 배포 링크 제출 필요)

**담당: 팀원 A** (9/13 역할 재조정 — 팀원 B는 데모 데이터 시딩 전담, 조장은 5-9번 트래픽 처리 전담).

레포를 나누지 않아도 배포는 문제없습니다. Vercel/Railway 모두 "레포 안 특정 하위 폴더만 배포"하는 옵션(Root Directory)을 지원합니다.

| 영역 | 플랫폼 | 비고 |
|---|---|---|
| 프론트엔드 | Vercel | Root Directory를 `frontend`로 지정. 무료 |
| 백엔드 + MySQL | Railway | Root Directory를 `backend`로 지정. MySQL 플러그인 추가 + Volume(영구 디스크)을 `CHROMA_PERSIST_DIR` 경로에 마운트 |

**중요**: ChromaDB는 로컬 파일로 데이터를 저장하는 방식이라, 서버가 재시작될 때 데이터가 사라지지 않으려면 반드시 Volume(영구 디스크)을 붙여야 합니다. 붙이지 않으면 배포 후 서버가 한 번이라도 재시작될 경우 업로드했던 인수인계서 임베딩이 전부 초기화됩니다.

**GitHub Actions(`.github/workflows/`) 파일은 만들지 않습니다.** Vercel/Railway 둘 다 GitHub 레포를 연결해두면 `main` 브랜치에 push할 때마다 자동으로 빌드·배포하는 기능을 자체 제공하므로, 별도 워크플로 설정이 필요 없습니다.

**배포 절차 (개략)**
1. Railway에 백엔드 레포 연결, Root Directory `backend` 지정
2. Railway에서 MySQL 플러그인 추가 → 자동 발급되는 접속 정보를 5-4번 환경변수(`MYSQL_HOST` 등)에 매핑
3. Railway 서비스에 Volume 추가 → `CHROMA_PERSIST_DIR` 경로에 마운트
4. Railway 환경변수 탭에 `OPENAI_API_KEY` 등 나머지 값 입력
4-1. **(신설, 9/13) Railway MySQL의 `max_connections`이 40 이상인지 확인할 것** — `core/database.py`가 DB 커넥션 풀을 최대 40개(`pool_size=20`+`max_overflow=20`)까지 쓰도록 설정돼 있음(5-9 참고, 부하 테스트로 실측 후 결정한 값). MySQL 기본값(151)이면 문제없지만, Railway 플랜에 따라 더 낮게 잡혀 있을 수 있으니 배포 후 한 번 확인
5. Vercel에 프론트엔드 레포 연결, Root Directory `frontend` 지정
6. 프론트엔드 `api/client.js`의 baseURL을 Railway가 발급한 백엔드 URL로 설정
7. 이후 `main`에 push할 때마다 양쪽 다 자동 재배포

## 5-9. 비용/트래픽 방어 (1차 빌드 필수)

**담당: 조장** (9/13 역할 재조정 — 팀원 A는 5-8번 배포를, 팀원 B는 6-6번 데모 데이터 시딩을 전담).

배포 링크가 심사위원뿐 아니라 투표 참여자에게도 공개되고, 이메일 인증이 없어 계정 생성 자체를 막을 수는 없기 때문에, LLM 호출 비용이 통제 밖으로 나가지 않도록 아래를 1차 빌드에 반드시 포함합니다.

**"트래픽" 방어 (9/13 실측으로 발견, 위 1~6번의 "비용" 방어와는 별개 문제)**: 동시에 많은 사람이 몰렸을 때 서버가 실제로 처리 가능한가의 문제.

- **[해결됨, 9/13] DB 커넥션 풀 부족** — `core/database.py`의 `create_engine()`이 풀 크기를 지정 안 해서 SQLAlchemy 기본값(5+10=15)을 쓰고 있었음. FastAPI가 동기(`def`) 라우터를 돌리는 스레드풀 상한(anyio 기본값 40)보다 훨씬 좁아서, 동시 요청 16개부터 DB 커넥션을 못 받아 대기하는 걸 부하 테스트(`/chat/ask` 15~18명 동시 요청)로 실측 확인함. `pool_size=20, max_overflow=20`(총 40, 스레드풀 상한과 동일 — 그 이상은 스레드 배정 자체가 안 돼서 의미 없는 숫자)으로 수정 완료. 배포 시 Railway MySQL의 `max_connections` 확인 필요(5-8번 4-1 참고, 팀원 A)
- **[해결됨, 9/14]** `document.py`의 `upload_document`가 `async def`인데 내부에서 동기(블로킹) 방식으로 OpenAI 임베딩을 호출해서, 인수인계서 업로드 중엔 그 순간 서버 전체(이벤트 루프)가 멈춰 다른 사용자의 챗봇 응답까지 같이 느려질 수 있는 문제가 있었음. `def`(동기)로 전환해서 나머지 라우터와 같은 패턴(스레드풀에서 실행)으로 통일 — 업로드 기능 자체(단일/복수 파일, label)는 재테스트로 정상 동작 확인함. 이걸로 5-9번 트래픽 방어 항목 완료.

**1) API 레벨 rate limit (코드, `slowapi`)**
- 대상: `/chat/ask`, `/checklist/draft`, `/report/generate` (OpenAI를 호출하는 세 엔드포인트)
- 사용자별(토큰의 `user_id` 기준) 제한 + IP별 전역 제한을 함께 건다 — `user_id`별 제한만으로는 계정을 계속 새로 만들어 우회하는 걸 막을 수 없기 때문
- 기준치(초안, 실측하며 조정): 사용자별 분당 10회, IP별 분당 20회
- 한도 초과 시 3-7번 공통 에러 포맷으로 429 응답

**2) 요청 크기 제한**
- `/chat/ask`의 `question`: 최대 500자
- `/document/upload`의 파일: 최대 10MB (초과 시 400)

**3) LLM 호출 파라미터 캡**
- 모든 OpenAI 호출에 `max_tokens` 상한을 건다
- 정확도가 상대적으로 덜 중요한 체크리스트 초안 생성(`/checklist/draft`)은 더 저렴한 모델 사용을 우선 검토

**4) `/report/generate` 최소 재생성 간격**
- 같은 `newcomer_id`에 대해 마지막 생성 후 일정 시간(예: 5분) 이내 재요청은 새로 계산하지 않고 최근 결과를 그대로 반환하거나 429 처리

**5) OpenAI 대시보드 하드 리밋 (코드 아님, 배포 전 운영 설정)**
- platform.openai.com → Settings → Billing → Limits에서 월 예산 상한을 설정
- 위 1~4번이 뚫리거나 버그가 나도 실제 과금이 한도 이상으로 나가지 않게 막는 최후 방어선 — 배포하기 전에 가장 먼저 설정

**6) 데모 계정과 1)의 충돌 방지** (신설 — 팀원 B 지적, B-3)
- 1-8번 데모 모드는 회사당 신입 계정 1개(+ B-4로 사수 계정 1개까지)를 여러 명이 동시에 로그인해서 씀. `/chat/ask`·`/checklist/draft`(신입 쪽 데모 계정 공유)뿐 아니라 `/report/generate`(사수 쪽 데모 계정 공유)도 마찬가지 문제 — 사용자별 제한이 순수하게 `user_id` 하나로만 걸리면, 심사 당일 같은 회사를 고른 여러 명이 **하나의 분당 10회 한도를 나눠 쓰는** 상태가 되어 기능이 정지한 것처럼 보일 수 있음
- 해결: 데모 계정 8개(신입 4 + 사수 4, 9/13 회사 3곳 → 4곳 확장 반영)의 `user_id`는 알려진 값이므로(6-6, `demo-newcomer-a`/`-b`/`-c`/`-d`, `demo-mentor-a`/`-b`/`-c`/`-d` 고정), rate limit의 사용자별 키 계산 시 이 계정들만 `user_id` 단독이 아니라 **`user_id` + 방문자 구분값**을 조합해서 키를 만든다
- 방문자 구분값은 IP가 아니라 **프론트가 브라우저마다 생성해서 보내는 `X-Visitor-Id` 헤더**(값 없으면 IP로 폴백)를 우선 사용 — 심사장처럼 여러 명이 같은 공용 WiFi(=같은 IP)를 쓰는 상황에서는 IP만으로 나눠도 여전히 한 버킷으로 묶이기 때문. IP별 전역 제한(1번의 IP 기준 20/분)은 원래도 이런 문제와 무관하므로 그대로 둠
