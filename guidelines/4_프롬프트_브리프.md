# 4. 팀원별 AI 프롬프트 브리프

> 각자 아래 자신의 브리프를 그대로 복사해서 Claude Code에 붙여넣고 작업을 시작하세요.
> 공통 전제: 백엔드 FastAPI + MySQL + ChromaDB, 프론트엔드 React, LLM은 OpenAI API, 다단계 로직(챗봇 답변 생성, 리포트 신호 계산, 체크리스트 초안 생성)은 LangGraph로 상태 관리하며 구현.

---

## 4-1. 조장 (챗봇 · 리포트 · 체크리스트 초안생성)

```
[역할]
나는 "신입 업무보조 챗봇 + 업무 적응도 리포트" 프로젝트에서 AI 파이프라인
(챗봇 RAG, 체크리스트 초안 생성, 리포트 생성) 전체를 담당한다.

[전체 컨텍스트]
- 백엔드: FastAPI + MySQL + ChromaDB
- LLM: OpenAI API
- 다단계 로직은 LangGraph로 상태 관리하며 구현한다 (조회 → 판단 → 생성 단계를
  명시적인 그래프로 구성)
- 이 모듈은 팀원 A(문서 처리·체크리스트 저장), 팀원 B(사용자·배정·프론트엔드)와
  병렬로 개발되며, 아래 스키마·API 형식을 반드시 지켜야 통합 시 충돌이 안 난다.

[내가 지켜야 할 데이터 모델] (guidelines/2_공통_데이터_모델.md 참조)
- DocumentChapter, DocumentChunk (읽기 전용 — 팀원 A가 생성)
- ChatLog (직접 생성)
- ChecklistItem (초안 생성 시 title/chapter_id만 반환, 저장은 하지 않음 — 저장은 팀원 A 담당)
- AdaptationReport, ReportSection (직접 생성)
- Assignment (읽기 전용 — 챗봇이 newcomer_id로 배정 문서를 조회할 때 사용)

[내가 구현해야 할 API] (guidelines/3_API_명세.md 3-3, 3-4, 3-6 참조)
- POST /chat/ask
- GET /chat/logs?newcomer_id=
- POST /checklist/draft
- POST /report/generate
- GET /report/{newcomer_id}
- GET /report/{newcomer_id}/history

[요구사항 — 챗봇]
- newcomer_id로 Assignment를 조회해 배정된 document_id를 먼저 확인하고,
  그 문서 범위로 ChromaDB 검색을 제한한다 (다른 신입의 문서는 검색하지 않음)
- 배정이 없는 newcomer_id로 요청이 오면 에러 응답 반환
- 검색 결과가 충분히 유사하지 않으면 answered=false, answer에는
  "문서에 없는 내용이니 담당자에게 문의하세요" 계열 고정 문구 사용
  (이 시점에 "문서를 보강하겠다"는 언급은 절대 하지 않는다 — 그건 리포트에서만 다룸)
- 답변 성공 시 matched_chapter_id는 실제 검색된 청크의 chapter_id
- 답변 실패 시 matched_chapter_id는 해당 문서의 챕터 제목 목록 중 LLM이 근접
  추정한 값(사후 추정), 추정도 어려우면 None

[요구사항 — 체크리스트 초안 생성]
- document_id에 해당하는 DocumentChapter를 순회하며, 각 챕터에서 신입이 실제로
  해봐야 할 태스크 후보를 생성
- 저장하지 않고 {title, chapter_id} 리스트만 반환 (미리보기)

[요구사항 — 리포트 생성]
- ChatLog(newcomer_id 기준) + ChecklistItem(newcomer_id 기준) 로그를 모아
  4개 신호 계산:
  - growth_curve: question_type 분포가 기간별로 어떻게 이동했는지
  - chapter_heatmap: matched_chapter_id별 질문 횟수
  - gap_task: 완료(completed_at 존재) 됐지만 완료 이후에도 관련 질문이 이어진 항목
  - silence_risk: 질문 빈도 급감 + 체크리스트 완료 속도 정체가 동시에 나타난 구간
- 각 신호별로 LLM이 summary(자연어 요약) 생성. 질문 원문은 그대로 노출하지 않고
  패턴 단위로만 서술
- 결과를 AdaptationReport로 저장 (generated_at은 실제 생성 시각)

[하지 말아야 할 것]
- 위에 정의된 필드명을 임의로 바꾸지 말 것
- 다른 모듈의 엔드포인트를 임의로 새로 만들지 말 것 (필요하면 먼저 팀에 공유)
- 답변 실패 케이스에서 신입에게 "문서를 보강하겠다"는 식의 문구를 절대 노출하지 말 것
```

## 4-2. 팀원 A (문서 처리 · 체크리스트 편집/저장)

```
[역할]
나는 "신입 업무보조 챗봇 + 업무 적응도 리포트" 프로젝트에서 인수인계서 문서 처리와
체크리스트 저장/관리를 담당한다.

[전체 컨텍스트]
- 백엔드: FastAPI + MySQL + ChromaDB
- 이 모듈은 조장(챗봇·리포트·초안생성), 팀원 B(사용자·배정·프론트엔드)와 병렬로
  개발되며, 아래 스키마·API 형식을 반드시 지켜야 통합 시 충돌이 안 난다.

[내가 지켜야 할 데이터 모델] (guidelines/2_공통_데이터_모델.md 참조)
- DocumentChapter, DocumentChunk (직접 생성)
- ChecklistItem (직접 생성)

[내가 구현해야 할 API] (guidelines/3_API_명세.md 3-2, 3-5 참조)
- POST /document/upload
- GET /document/{document_id}/chapters
- POST /checklist
- GET /checklist?newcomer_id=
- PATCH /checklist/{item_id}
- PATCH /checklist/{item_id}/reorder
- POST /checklist/{item_id}/complete

[요구사항 — 문서 처리]
- 업로드된 인수인계서를 목차(장-절) 단위로 파싱해 DocumentChapter로 저장
  (chapter_id는 문서 내에서만 고유하면 됨, document_id로 문서를 구분)
- 각 챕터를 다시 검색용 단위로 청킹해서 DocumentChunk 생성, 임베딩 계산 후
  ChromaDB에 저장 (chunk 저장 시 document_id, chapter_id 태그 필수)
- 청킹 기준(문단 단위/글자 수 기준 등)은 자유롭게 정해도 됨

[요구사항 — 체크리스트]
- 사수가 항목을 직접 입력하거나(source="manual"), 조장의 /checklist/draft
  응답을 검토·수정 후 저장(source="ai_draft")하는 두 경로를 모두 지원
- newcomer_id는 필수 — 저장 시 반드시 함께 받아야 함
- chapter_id는 선택 — 문서와 무관한 항목(예: "옆자리 동료와 인사하기")도 허용
- 완료 체크는 검증 절차 없이 시각만 기록 (신입이 직접 완료 버튼을 누르는 셀프 체크)

[하지 말아야 할 것]
- 위에 정의된 필드명을 임의로 바꾸지 말 것
- 체크리스트를 문서에서 자동 생성하는 로직을 이 모듈에 넣지 말 것 (그건 조장 담당,
  이 모듈은 저장·편집만 담당)
- 다른 모듈의 엔드포인트를 임의로 새로 만들지 말 것
```

## 4-3. 팀원 B (사용자/배정 · 프론트엔드)

```
[역할]
나는 "신입 업무보조 챗봇 + 업무 적응도 리포트" 프로젝트에서 사용자/배정 관리
백엔드와 신입·HR 두 화면의 프론트엔드 전체를 담당한다.

[전체 컨텍스트]
- 백엔드: FastAPI + MySQL
- 프론트엔드: React
- 이 모듈은 조장(챗봇·리포트·초안생성), 팀원 A(문서 처리·체크리스트 저장)와 병렬로
  개발되며, 아래 스키마·API 형식을 반드시 지켜야 통합 시 충돌이 안 난다.
- 다른 두 모듈의 API는 아직 구현 중일 수 있으니, mock 데이터로 화면을 먼저 완성해도 된다.

[내가 지켜야 할 데이터 모델] (guidelines/2_공통_데이터_모델.md 참조)
- User (직접 생성)
- Assignment (직접 생성)
- 나머지 모델(ChatLog, ChecklistItem, AdaptationReport 등)은 API 응답으로만 받아서
  화면에 표시 — 직접 생성하지 않음

[내가 구현해야 할 API] (guidelines/3_API_명세.md 3-1 참조)
- POST /user/register
- GET /user/{user_id}
- POST /assignment
- GET /assignment?newcomer_id=
- GET /assignment?mentor_id=

[요구사항 — 사용자/배정]
- 정식 인증(비밀번호 등) 없이 이름+역할 입력만으로 User 생성
- 발급받은 user_id는 프론트엔드에서 보관(localStorage 등)해서, 같은 브라우저로
  재접속 시 재입력 없이 이어서 쓸 수 있게 처리
- 신입이 자기 사수 이름을 보고 싶을 때는 GET /assignment?newcomer_id= 로
  mentor_id를 받은 뒤, GET /user/{mentor_id}로 이름을 조회하는 방식으로 처리
  (별도 통합 API 없음)

[요구사항 — 화면 구성]
공통(최초 진입): 이름 + 역할(신입/사수) 입력 화면

HR/사수 화면:
- 인수인계서 업로드 (POST /document/upload 연동, 팀원 A API)
- 담당 신입 배정 (POST /assignment)
- 체크리스트 작성/수정 — 직접 작성 또는 "인수인계서 기반 초안 생성"
  (POST /checklist/draft로 미리보기 → 수정 → POST /checklist로 저장, 조장·팀원 A API 연동)
- 적응도 리포트 열람 — 최신 리포트(GET /report/{newcomer_id}) +
  생성 버튼(POST /report/generate, 기간은 자동 계산해서 채움) +
  히스토리(GET /report/{newcomer_id}/history) (조장 API 연동)

신입사원 화면:
- 챗봇 대화 (POST /chat/ask 연동, 조장 API)
- 체크리스트 확인/완료 체크 (GET /checklist?newcomer_id=,
  POST /checklist/{item_id}/complete, 팀원 A API 연동)
- 리포트는 노출하지 않음

[하지 말아야 할 것]
- 위에 정의된 필드명을 임의로 바꾸지 말 것
- 신입 화면에 리포트나 답변 실패 시 "문서 보강" 관련 내용을 노출하지 말 것
- 다른 모듈의 엔드포인트를 임의로 새로 만들지 말 것
```
