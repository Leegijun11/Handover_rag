# 1. 시스템 개요

## 1-1. 사용자 구분과 연결 구조

이 앱은 세 종류의 개념을 다룹니다: **신입사원(newcomer)**, **사수/기존사원(mentor)**, 그리고 이 둘을 이어주는 **배정(Assignment)**.

- 1차 빌드에서는 이메일 인증은 구현하지 않지만, 이메일+비밀번호 기반 회원가입/로그인과 JWT 세션은 구현합니다. 최초 진입 시 이름·이메일·비밀번호·역할(신입/사수)을 입력받아 `User`를 생성하고, 로그인 시 발급되는 JWT(`access_token`)를 프론트엔드가 보관해 이후 모든 요청의 `Authorization: Bearer <token>` 헤더에 실어 보냅니다. (이메일 실제 인증 메일 발송은 2차 확장 항목 — 심사 링크가 공개되는 1차 빌드 특성상 가입 절차를 무겁게 만들지 않기 위함, 6-4 참고)
- 사수가 인수인계서를 업로드한 뒤, 그 문서를 특정 신입 한 명에게 **배정(Assignment)**해야 그 신입이 챗봇·체크리스트를 사용할 수 있습니다.
- 사수 한 명이 여러 신입을 동시에 담당할 수 있고(1:N), 여러 사수가 각자 다른 신입에게 각자의 인수인계서를 배정하는 것도 가능합니다 — 즉 여러 팀의 여러 사수가 동시에 이 앱을 쓰는 상황을 전제로 설계합니다.

**담당**: 팀원 B (화면 + 이 기능에 필요한 간단한 백엔드 API 포함)

---

## 1-2. 화면 구성 (담당: 팀원 B)

**공통 (최초 진입)**
- 회원가입 화면 (이름 + 이메일 + 비밀번호 + 역할(신입/사수))
- 로그인 화면 (이메일 + 비밀번호)

**HR/사수 화면**
- 인수인계서 업로드
- 담당 신입 배정(Assignment 생성)
- 체크리스트 작성/수정
- 적응도 리포트 열람

**신입사원 화면**
- 챗봇 대화
- 체크리스트 확인/완료 체크

> 리포트는 신입사원 화면에 노출되지 않음 (HR 전용)

---

## 1-3. 로직 모듈 구성

| 모듈 | 담당 | 역할 |
|---|---|---|
| 사용자/배정 관리 | 팀원 B | 사용자 등록, 신입-사수-문서 배정 |
| 문서 처리 | 팀원 A | 인수인계서 업로드 → 청킹 → 임베딩 |
| 체크리스트 (편집/저장) | 팀원 A | 항목 작성·수정·저장, 완료 체크 관리 |
| 체크리스트 (초안 생성) | 조장 | 문서 챕터 기반 LLM 태스크 후보 생성 |
| 챗봇 (RAG) | 조장 | 질문 → 배정된 문서 범위에서 벡터 검색 → 답변 생성 → 출처 표시 |
| 리포트 생성 | 조장 | 로그 집계 → 적응도 신호 계산 → LLM 요약 |

---

## 1-4. 데이터 저장소

| 저장소 | 용도 |
|---|---|
| ChromaDB | 인수인계서 임베딩, 벡터 검색 (문서 단위로 필터링) |
| MySQL | 사용자, 배정, 문서 메타데이터, 챕터 구조, 체크리스트, 질문 로그, 리포트 등 정형 데이터 |

---

## 1-5. 계층 간 연결 규칙

- 화면 계층은 API(3번 섹션 명세)를 통해서만 로직 계층과 통신한다
- 로직 계층 내 모듈 간 데이터 교환은 공통 데이터 모델(2번 섹션)을 따른다
- 체크리스트 초안 생성(조장)은 DocumentChapter(MySQL)만 읽고, 편집·저장(팀원 A)도 MySQL만 사용한다 (ChromaDB 접근 없음)
- 챗봇(조장)은 신입의 `user_id`로 Assignment를 조회해 배정된 `document_id`를 확인한 뒤, 그 문서 범위 안에서만 ChromaDB를 검색한다 — 다른 신입에게 배정된 문서는 검색 대상에서 제외된다

---

## 1-6. 핵심 시나리오 흐름 (순서대로)

1. **사용자 등록**
   - 담당: 팀원 B → 이름 + 역할 입력받아 `User` 생성
   - 신입/사수 모두 이 단계를 거쳐야 이후 기능 사용 가능

2. **인수인계서 업로드**
   - 사수가 문서 업로드
   - 담당: 팀원 A → 청킹·임베딩 후 ChromaDB에 저장, 챕터 구조는 MySQL에 저장 (문서 단위 `document_id` 발급)

3. **신입 배정**
   - 담당: 팀원 B → 사수가 업로드한 문서를 특정 신입 한 명과 연결 (`Assignment` 생성)
   - 이 단계가 끝나야 해당 신입이 챗봇을 사용할 수 있음

4. **체크리스트 작성**
   - 담당: 팀원 A → 항목 입력·수정 화면, 저장 API
   - 담당: 조장 → 인수인계서 챕터 기반 체크리스트 초안 생성 API (LLM)
   - 사수가 직접 작성하거나, AI 초안을 검토·수정 후 저장 (원할 경우 관련 문서 챕터 선택적 연결)

5. **신입 질문 처리**
   - 신입사원이 챗봇에 질문 입력
   - 담당: 조장 → Assignment로 배정 문서 확인 → 해당 문서 범위에서 ChromaDB 검색 → 답변 생성 → 질문 로그(ChatLog) 저장
   - 매칭되는 문서가 없으면: 신입 화면에는 "문서에 없는 내용이니 담당자에게 문의하세요"만 노출 (문서 보강 언급 없음)

6. **체크리스트 완료 처리**
   - 신입사원이 항목을 스스로 완료 체크
   - 담당: 팀원 A → 완료 시각을 MySQL에 기록

7. **적응도 리포트 생성 (사수가 요청 시)**
   - 담당: 조장 → 질문 로그 + 체크리스트 완료 로그를 모아 신호(성장곡선/영역별 히트맵/완료-이해 불일치/침묵 위험) 계산
   - 각 신호에 대해 LLM이 요약 코멘트 생성 → HR 화면에 리포트로 제공

---

## 1-7. 이 구조에서 지켜야 할 원칙

- 신입 화면과 HR 화면은 데이터 접근 범위가 다르다 (리포트는 HR 전용)
- 답을 못 찾은 질문은 그 즉시 "문서 보강"으로 연결하지 않는다 — 신입에게는 사람에게 문의하라고만 안내하고, 문서 보강 여부는 별도로 HR에게만 주기적으로 리포트된다
- 체크리스트 완료는 검증 절차 없는 셀프 체크이며, 이 느슨함 자체가 리포트 신호(완료-이해 불일치)의 재료로 쓰인다
- 챗봇은 항상 신입 본인에게 배정된 문서 범위 안에서만 검색한다 — 배정되지 않은 문서, 다른 신입의 문서는 검색 대상이 아니다
- 사수는 여러 신입을 동시에 담당할 수 있으며, 리포트도 신입별로 독립적으로 생성된다
