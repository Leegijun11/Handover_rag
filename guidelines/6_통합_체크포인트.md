## 6-3. 통합 테스트 시나리오 (9/16~9/17에 반드시 통과할 흐름)

1. 사수 계정으로 `User` 등록 후 로그인 → `access_token` 발급 확인
2. 신입 계정으로 `User` 등록 후 로그인 → `access_token` 발급 확인
3. 사수가 인수인계서 업로드 → `DocumentChapter`/`DocumentChunk` 생성 확인
4. 사수가 해당 신입에게 문서 배정 (`Assignment` 생성)
5. 사수가 체크리스트 작성 — 직접 작성 1건 + AI 초안 생성 후 승인 1건
6. 신입이 챗봇에 질문 2건 이상 (문서에 있는 내용 1건, 없는 내용 1건 — 두 경우 모두 정상 동작하는지)
7. 신입이 체크리스트 항목 1건 이상 완료 체크
8. 사수가 리포트 생성 요청 → 4개 신호가 모두 빈 값 없이 채워지는지 확인
9. 사수가 리포트 히스토리 조회 → 방금 생성한 리포트가 목록에 있는지 확인

이 9단계가 배포된 링크에서 한 번에 끊기지 않고 통과하면, 데모 시연 준비는 끝난 것으로 봅니다.

## 6-5. 2차 확장 항목 (1차 빌드 범위 밖)

1차 빌드(9/20 제출)는 이메일 인증 없이 이메일+비밀번호+JWT까지만 구현합니다(1번 문서 §1-1, 3번 문서 §3-9). 아래는 1차에는 넣지 않고, **예선 통과가 확정된 뒤** 필요 여부를 다시 판단하는 항목입니다 — 지금 임의로 구현하지 마세요.

| 항목 | 내용 |
|---|---|
| 이메일 인증 | 회원가입 시 실제 인증 메일 발송·클릭 확인 절차 추가 |
| 비밀번호 재설정 | 이메일 인증이 선행되어야 의미가 있어 함께 묶임 |
| Refresh token | 지금은 access token 단일 발급 + 만료 시 재로그인. 세션 유지가 중요해지면 도입 검토 |

이 표에 항목을 추가하거나 착수 시점을 앞당길 필요가 생기면(예선 결과와 무관하게), 조장에게 먼저 공유 후 이 문서를 갱신합니다.

## 6-6. 데모 시드 데이터 준비 (배포 전 1회, 1-8 참고)

배포된 링크에서 "데모로 체험하기"가 바로 동작하려면, 심사 전에 회사 3곳 분량의 데모 데이터를 미리 만들어둬야 합니다.

- `backend/scripts/seed_demo.py` (신규) — 회사 3곳 각각에 대해 사수/신입 `User`, 인수인계서(`Document`/`DocumentChapter`/`DocumentChunk`), `Assignment`, 체크리스트(완료/미완료 섞어서 5개 내외)를 생성하는 1회성 스크립트
- 이미 구현된 각자의 등록/로그인/업로드/배정/체크리스트 로직을 그대로 재사용해서 만든다 (별도 SQL을 새로 짜지 않음)
- **신입뿐 아니라 사수 계정으로도 데모 로그인이 가능해야 하므로(1-8, B-4), 신입의 질문 로그·체크리스트 완료가 어느 정도 쌓인 상태를 시딩한 뒤 `POST /report/generate`까지 1회 호출해서 `AdaptationReport`도 미리 만들어둔다** — 안 그러면 사수 데모 계정으로 리포트 화면에 들어갔을 때 빈 화면만 보임
- 실행 시점: 9/16~9/17 통합 테스트 통과 후, 9/18 배포 확정 전에 1회 실행 (Railway MySQL/ChromaDB에 반영)
- 담당: 조장이 조율 — User·Document·Assignment·Checklist·Report 전 모듈에 걸쳐 있어서, 각자 자기 담당 모델 생성 부분만 스크립트에 채워 넣는 방식으로 진행
- 데모 계정의 이메일/비밀번호는 프론트엔드 상수로 하드코딩 (실 사용자 계정이 아니라 공개해도 무방한 값)
- **신입 계정 3개뿐 아니라 사수 계정 3개도, 일반 회원가입처럼 매번 랜덤 UUID로 발급하지 말고 스크립트에 고정값(`demo-newcomer-a`/`-b`/`-c`, `demo-mentor-a`/`-b`/`-c`)으로 직접 지정해서 만든다** — 그래야 `.env`의 `DEMO_USER_IDS`(5-9번 항목 6, rate limit 예외 처리용)와 항상 값이 일치하고, "시딩 → user_id 확인 → .env에 붙여넣기"라는 수동 동기화 단계 자체가 사라짐. 사수 계정도 넣어야 하는 이유: `POST /report/generate`도 OpenAI를 호출하는 mentor 전용 API라, 심사위원이 "사수로 체험" 중 리포트를 실시간으로 재생성하면 데모 사수 계정도 신입 계정과 똑같이 여러 명이 공유하는 문제가 생김

## 6-7. 통합 후 실험 과제: 챗봇 출처 표시(`matched_chapter_id`) 방식 재검토

**배경**: 챗봇(`backend/routers/chat.py`)이 ChromaDB에서 유사도 상위 3개 청크를 가져와 답변 생성엔 3개 다 근거로 쓰지만, 출처(`matched_chapter_id`)는 1등 청크의 챕터 하나만 기록함. 만약 1등과 2등·3등의 유사도 차이가 실제로는 미미한 경우가 흔하다면(=여러 챕터가 비슷한 비중으로 관련 있는 질문이 많다면), 출처를 하나만 보여주는 게 오히려 부정확한 인상을 줄 수 있음.

**할 일** (3개 브랜치 병합 후, 실제 인수인계서 데이터로 테스트 가능해지면 진행 — 지금은 미착수):
1. `SIMILARITY_THRESHOLD`(`chat.py`, 현재 0.75는 가설값)를 실측 데이터로 조정
2. 동시에, 검색 결과 1위와 2위·3위의 유사도(`distance`) 차이가 유의미한지 측정 — 차이가 거의 없는 케이스가 자주 나오는지 확인
3. 차이가 흔하지 않다면 지금 방식(1등만 출처 표시) 유지. **흔하다면**, 상위 N개(예: distance 차이가 임계값 이내인 것들)를 전부 "참고한 챕터"로 보여주는 방향으로 재설계

**영향 범위 — 스키마 변경 가능성 있음**: 지금 `matched_chapter_id`는 `ChatLog`(2번 문서)와 `/chat/ask` 응답의 `source_chapter_id`(3-3) 둘 다 단일 값(`str | None`)으로 고정돼 있음. 여러 챕터를 보여주는 쪽으로 바뀌면 이 두 곳을 리스트 타입으로 바꿔야 하므로, 결정되면 2번·3번 문서부터 먼저 고치고 코드에 반영할 것 (0번 문서의 변경 통제 원칙 — 조장 본인 결정이라도 문서에 먼저 반영 후 구현).
